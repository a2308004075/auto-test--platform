## 2. 项目管理

### 2.1 【PM-001】项目列表

#### 2.1.1 需求描述

项目是平台的一级组织单元，所有接口、关键字、用例、环境等资源均归属于项目。项目列表作为平台首页入口，以卡片视图展示所有项目并提供搜索、筛选能力，帮助用户快速定位并进入目标项目。

#### 2.1.2 业务规则

##### 2.1.2.1 项目列表展示

背景：用户进入平台后首先需要选择目标项目进入工作空间，列表以卡片视图展示所有项目。

需求：
1. 以卡片网格布局（3 列）展示所有项目，仅支持卡片视图
2. 支持按项目名称模糊搜索
3. 支持按项目状态（全部/启用/停用）筛选
4. 项目卡片显示：名称、描述（两行截断）、统计信息（接口数、关键字数、Action 数、用例数、测试套件数、测试计划数）、创建时间
5. 分页展示，每页 9 个项目
6. 非 admin 用户隐藏新建、编辑、启停、删除按钮，但可查看禁用项目
7. 点击启用状态的项目卡片进入项目概览，禁用项目不可点击进入

| 变更点 | 变更前 | 变更后 |
|--------|--------|--------|
| 项目列表入口 | 无（新平台） | 平台首页展示所有项目卡片，支持搜索、筛选、分页 |
| 项目卡片信息 | 无 | 展示名称、描述（截断）、接口数、关键字数、Action 数、用例数、测试套件数、测试计划数、创建时间 |
| 视图模式 | 无 | 仅卡片视图 |

##### 2.1.2.2 新建项目

背景：用户需要为新测试项目创建独立工作空间。

需求：
1. 点击「新建项目」按钮弹出创建弹窗
2. 填写项目名称（必填）、描述（可选）
3. 创建成功后自动跳转至项目概览页

#### 2.1.3 操作步骤

| 步骤 | 说明 |
|------|------|
| 1. 登录平台进入首页 | 展示项目列表页，卡片视图，页面标题「项目管理」，右侧「新建项目」主按钮（仅 admin 可见） |
| 2. 搜索/筛选项目 | 工具栏搜索框输入名称模糊搜索，状态下拉筛选（全部/启用/停用） |
| 3. 点击项目卡片进入 | 点击启用状态的项目卡片进入项目概览，禁用项目不可点击 |
| 4. 编辑/启停/删除项目 | 卡片底部操作区：编辑按钮、启停按钮、删除按钮（仅 admin 可见） |
| 5. 新建项目 | 点击「新建项目」→ 弹窗填写名称、描述 → 确认创建 |

#### 2.1.4 字段说明

| 字段 | 来源 | 说明 | 协议 |
|------|------|------|------|
| 项目名称 | 用户输入 | 必填，最长 50 字符，不可重复 | `POST /api/projects` → `name` |
| 描述 | 用户输入 | 可选，最长 200 字符，卡片展示最多两行，超出截断 | `POST /api/projects` → `description` |
| 状态 | 系统生成 | 启用 = 绿色 tag，停用 = 灰色 tag；新建默认启用 | `PATCH /api/projects/:id/status` → `status` |

| 关键字数 | 系统统计 | 项目下接口关键字总数 | `GET /api/projects/:id/dashboard` → `keyword_count` |
| Action 数 | 系统统计 | 项目下 Action 关键字总数 | `GET /api/projects/:id/dashboard` → `action_count` |
| 用例数 | 系统统计 | 项目下所有启用用例的总数 | `GET /api/projects/:id/dashboard` → `case_count` |

| 创建时间 | 系统生成 | 项目创建时间，卡片底部显示 | `GET /api/projects` → `created_at` |

### 2.2 【PM-002】项目概览

#### 2.2.1 需求描述

项目概览是进入项目后的首屏页面，以单页纵向滚动的五层渐进式信息架构（项目信息头部 → 质量健康度大卡片 → 核心 KPI 指标卡片 → 趋势分析区 → 覆盖率与风险监控），聚焦于测试质量反馈和测试 KPI 统计，帮助项目 Leader 和测试人员在一个页面内快速了解项目测试全貌。每个指标均配备 ⓘ 悬浮提示按钮，鼠标悬浮时显示指标说明。

#### 2.2.2 业务规则

##### 2.2.2.1 质量健康度面板（Layer 2）

背景：用户进入项目后需要一个直观的综合评分来快速判断项目测试质量水平。

需求：
1. 左侧：大号圆形进度环展示健康度评分（0-100分），中央数字 + 等级标签（≥90 优秀 / ≥75 良好 / ≥60 一般 / <60 较差）
2. 右侧：4 个评分维度进度条，每个维度带 ⓘ 提示按钮说明评分算法：
   - 通过率得分（权重 35%）
   - 覆盖率得分（权重 25%）
   - 稳定性得分（权重 25%）
   - 效率得分（权重 15%）
3. 综合评分 = 通过率得分×35% + 覆盖率得分×25% + 稳定性得分×25% + 效率得分×15%

##### 2.2.2.2 核心 KPI 指标卡片（Layer 3）

背景：用户需要快速了解测试资源规模、执行效果和质量健康度的多维度数据。

需求：
1. 8 个 KPI 卡片按 2 行 × 4 列网格排列，每卡片包含图标、指标名称 + ⓘ 提示按钮、指标值、底部趋势/辅助信息

### 4.2 【API-002】Swagger 导入（分步向导）

#### 4.2.1 需求描述

Swagger 导入通过三步向导（上传文件 → 解析预览 → 确认导入）将 Swagger 2.0 JSON 文件中的接口定义批量导入平台，支持增量导入。

#### 4.2.2 业务规则

##### 4.2.2.1 上传文件 & 选择分组

背景：用户需要将 Swagger 文件中的接口定义导入平台，需选择目标分组方式。

需求：
1. 上传 Swagger 2.0 JSON 文件（拖拽或点击上传）
2. 选择目标接口分组方式（单选）：
   - 导入到已有分组（下拉选择）
   - 创建新分组（输入分组名称 + 服务前缀）

##### 4.2.2.2 解析预览

需求：
1. 自动解析 `paths`（接口路径和 HTTP 方法）、`parameters`（参数）、`definitions`（`$ref` 引用和嵌套 DTO）
2. 展示解析结果列表，支持勾选要导入的接口
3. 增量导入：已有接口按 path+method 匹配更新，不删除多余接口
4. 底部统计：新增 N 条，更新 M 条

| 变更点 | 变更前 | 变更后 |
|--------|--------|--------|
| Swagger 导入 | 手动执行代码生成脚本 | 三步向导界面，上传 → 预览 → 确认，自动解析并写入数据库 |
| 增量导入 | 无 | 已有接口按 path+method 匹配更新，新增接口追加，不删除多余接口 |

Swagger 导入整体流程：

```
┌─────────────────────────────────────────────────────────────────────┐
│  步骤一：上传文件 & 选择分组                                           │
│  ┌──────────┐    ┌──────────────────┐    ┌────────────────────┐     │
│  │ 上传      │───▶│ 选择分组方式       │───▶│ 点击「下一步」       │     │
│  │ Swagger   │    │ ○ 已有分组(下拉)  │    │                    │     │
│  │ 2.0 JSON  │    │ ○ 创建新分组      │    │                    │     │
│  └──────────┘    └──────────────────┘    └────────┬───────────┘     │
└───────────────────────────────────────────────────┼─────────────────┘
                                                    ▼
```

### 4.5 【API-005】接口删除保护

#### 4.5.1 需求描述

接口删除时必须执行依赖检查，禁止直接删除被关键字或用例引用的接口，防止破坏下游依赖。

#### 4.5.2 业务规则

##### 4.5.2.1 删除依赖检查

背景：接口是关键字和测试步骤的基础数据，删除被引用的接口会导致关联关键字和用例失效。

需求：
1. 删除接口前自动检查关联关键字（ApiKeyword.endpoint_id）
2. 无关联 → 允许删除
3. 有关联 → 拒绝删除，展示依赖详情弹窗

| 变更点 | 变更前 | 变更后 |
|--------|--------|--------|
| 接口删除 | 无保护机制 | 删除前自动检查依赖，被引用接口禁止删除并展示依赖详情 |

依赖检查流程：

```
删除接口
  ↓
检查关联关键字（ApiKeyword.endpoint_id）
  ├── 无关联 → 允许删除
  └── 有关联 → 拒绝删除，展示依赖详情
          ↓
       列出所有关联关键字（名称、所属模块、关联用例数）
          ↓
       每个关联关键字 → 列出引用该关键字的测试用例（名称、所属套件、优先级）
```

解除依赖路径：
- 进入关键字详情，取消关联该接口
- 删除不再需要的关键字（需先解除与用例的关联）
- 从用例步骤中移除引用该关键字的步骤

### 4.6 【API-006】接口同步

#### 4.6.1 需求描述

支持重新上传 Swagger 文件与现有接口对比同步，展示差异（新增/参数变更/已废弃），确认后执行同步更新，并提供同步历史记录查看能力。

#### 4.6.2 业务规则

##### 4.6.2.1 上传文件与对比

背景：被测系统接口随版本迭代持续变化，需要定期将最新 Swagger 文件与平台已导入的接口进行对比同步，保持接口定义一致。

需求：
1. 上传 Swagger 2.0 JSON 文件，选择目标接口分组
2. 系统自动解析 Swagger 文件，与分组内现有接口按 `path + method` 逐一比对
3. 差异分类展示：
   - **新增接口**：Swagger 中存在但平台不存在的接口（蓝色 tag）
   - **参数变更**：path+method 匹配但参数定义（参数名/类型/必填/请求体 Schema）有变化的接口（橙色 tag）
   - **已废弃接口**：平台存在但 Swagger 中不存在的接口（红色 tag）
4. 用户可勾选要同步的接口（默认全选新增和变更，已废弃默认不勾选）

| 变更点 | 变更前 | 变更后 |
|--------|--------|--------|
| 接口同步 | 无（新平台） | 上传 Swagger 文件与现有接口对比，展示差异后确认同步 |
| 废弃接口处理 | 无 | 标记为已废弃（红色 tag），用户可选择保留或删除 |

##### 4.6.2.2 确认同步与执行

需求：
1. 展示同步摘要：新增 N 条、更新 M 条、废弃 K 条
2. 确认后执行同步：
   - 新增接口：写入数据库，关联到目标分组
   - 参数变更接口：更新参数定义（parameters、request_body、responses），保留接口 ID 不变
   - 已废弃接口（用户勾选删除的）：执行依赖检查，无依赖的直接删除，有依赖的标记为「已废弃」状态保留
3. 同步完成后展示结果报告：成功数、跳过数、失败数

接口同步执行流程：

```
上传 Swagger 文件 + 选择分组
  ↓
解析 Swagger，按 path+method 与分组内接口逐一比对
  ↓
┌──────────────────────────────────────────────────────┐
│                    差异分类                           │
│  ┌────────────┐  ┌────────────┐  ┌────────────────┐  │
│  │ 新增接口    │  │ 参数变更    │  │ 已废弃接口      │  │
│  │ (蓝色 tag)  │  │ (橙色 tag)  │  │ (红色 tag)     │  │
│  │ 默认全选    │  │ 默认全选    │  │ 默认不勾选      │  │
│  └──────┬─────┘  └──────┬─────┘  └───────┬────────┘  │
│         └───────────────┼────────────────┘            │
│                         ▼                             │
│              用户勾选要同步的接口                       │
└─────────────────────────┬────────────────────────────┘
                          ▼
              确认同步（展示摘要 N+M+K）
                          ▼
         ┌────────────────┼────────────────┐
         ▼                ▼                ▼
    新增接口         参数变更接口      已废弃接口(勾选删除)
    写入数据库       更新参数定义      执行依赖检查
    关联分组         保留接口ID         ┌────┴────┐
                                       ▼         ▼
                                   无依赖     有依赖
                                   直接删除   标记「已废弃」保留
                          ▼
              展示同步结果报告（成功/跳过/失败）
```

##### 4.6.2.3 同步历史记录

需求：
1. 记录每次同步操作：同步时间、操作人、Swagger 文件名、同步结果统计
2. 同步历史列表展示最近 20 次记录

#### 4.6.3 操作步骤

| 步骤 | 说明 |
|------|------|
| 1. 进入接口文档页，点击「同步 Swagger」按钮 | 弹出同步向导弹窗，步骤条显示：① 上传文件 → ② 对比预览 → ③ 确认同步 |
| 2. 上传 Swagger 文件并选择分组 | 拖拽或点击上传 Swagger 2.0 JSON 文件，下拉选择目标接口分组 |
| 3. 点击「开始对比」 | 系统解析文件并与分组内现有接口对比，展示差异列表 |
| 4. 查看差异并勾选 | 查看新增（蓝色）/变更（橙色）/废弃（红色）接口列表，勾选要同步的项 |
| 5. 点击「确认同步」 | 展示同步摘要（新增 N + 更新 M + 废弃 K），确认后执行 |
| 6. 查看同步结果 | 展示同步结果报告（成功数/跳过数/失败数），点击「完成」关闭弹窗 |
| 7. 查看同步历史（可选） | 点击「同步历史」按钮查看最近同步记录列表 |

#### 4.6.4 字段说明

| 字段 | 来源 | 说明 | 协议 |
|------|------|------|------|
| Swagger 文件 | 用户上传 | Swagger 2.0 JSON 文件，最大 10MB | `POST /api/projects/:pid/apis/sync` → `file` (multipart) |
| 目标分组 | 用户选择 | 对比范围的接口分组 | `POST /api/projects/:pid/apis/sync` → `group_id` |
| 差异类型 | 系统计算 | `added` / `updated` / `deprecated` | 响应 → `diff[].type` |
| 差异详情 | 系统计算 | 参数变更的具体字段差异 | 响应 → `diff[].changes` |
| 同步时间 | 系统生成 | 同步操作的时间戳 | `sync_history[].synced_at` |
| 同步结果 | 系统统计 | 新增数、更新数、废弃数、失败数 | `sync_history[].result` |

#### 4.7.1 需求描述

1. 批量启用：将选中的接口状态设为启用（`is_active = true`）

### 4.8 接口协议

#### 接口分组 API

| 方法 | 路径 | 说明 | 请求参数 | 响应 |
|------|------|------|----------|------|
| GET | `/api/projects/:project_id/api-groups` | 分组列表 | — | `ApiGroup[]`（含 id, name, prefix, api_count, is_system） |
| POST | `/api/projects/:project_id/api-groups` | 创建分组 | `{ name, prefix? }` | `ApiGroup` |
| PUT | `/api/projects/:project_id/api-groups/:id` | 更新分组 | `{ name?, prefix? }` | `ApiGroup` |
| DELETE | `/api/projects/:project_id/api-groups/:id` | 删除分组 | — | `{ message: string }` |

**默认分组规则：**

- 每个项目初始化时自动创建两个系统默认分组：「全部」和「未分组」。
- 系统默认分组通过 `is_system: true` 标识，**不允许编辑和删除**。
- 「全部」用于展示该项目下所有接口，不存储实际接口归属。
- 「未分组」用于收纳未指定自定义分组的接口；删除自定义分组时，其下的接口自动归入「未分组」。
- 用户新建分组时，名称不能与「全部」「未分组」重复。

#### 接口文档 API

| 方法 | 路径 | 说明 | 请求参数 | 响应 |
|------|------|------|----------|------|
| GET | `/api/projects/:project_id/apis` | 接口列表 | `group_id?`, `method?`, `source?`, `keyword?`, `page`, `page_size` | `{ items: Api[], total: int }` |
| POST | `/api/projects/:project_id/apis` | 创建接口 | `{ name, path, method, group_id, description?, parameters?, request_body?, responses? }` | `Api` |
| GET | `/api/projects/:project_id/apis/:id` | 接口详情 | — | `Api`（含完整参数定义） |
| PUT | `/api/projects/:project_id/apis/:id` | 更新接口 | 同创建参数 | `Api` |
| DELETE | `/api/projects/:project_id/apis/:id` | 删除接口 | — | `{ message }` 或 `409 { dependencies }` |
| GET | `/api/projects/:project_id/apis/:id/dependencies` | 查询依赖 | — | `{ keywords: [...], cases: [...] }` |

### 5.4 【KW-004】接口关键字删除保护

#### 5.4.1 需求描述

被 Action 引用的接口关键字不可直接删除，需先解除 Action 引用，防止破坏下游依赖。

#### 5.4.2 业务规则

##### 5.4.2.1 删除依赖检查

背景：接口关键字是 Action 关键字的组成单元，删除被引用的接口关键字会导致 Action 编排断裂、用例执行失败。

需求：
1. 删除前自动检查是否被 Action 引用（通过 Action.nodes 中的 keyword_id 关联）
2. 无引用 → 弹出确认弹窗「确定删除该接口关键字？」，确认后删除
3. 有引用 → 拒绝删除，展示依赖详情弹窗

| 变更点 | 变更前 | 变更后 |
|--------|--------|--------|
| 关键字删除 | 无保护机制 | 删除前自动检查 Action 引用，被引用的关键字禁止删除并展示依赖详情 |

依赖检查流程：

```
删除接口关键字
  ↓
检查 Action 引用（Action.nodes[].keyword_id）
  ├── 无引用 → 弹出确认弹窗 → 确认删除
  └── 有引用 → 拒绝删除，展示依赖详情弹窗
          ↓
       列出所有引用该关键字的 Action（名称、分类、被用例引用数）
          ↓
       每个 Action → 列出引用该 Action 的测试用例（名称、所属套件、优先级）
```

解除依赖路径：
- 方式一：进入 Action 编辑器，移除引用该关键字的节点
- 方式二：删除不再需要的 Action（需先解除 Action 与用例的关联）
- 方式三：从用例步骤中移除引用该 Action 的步骤

#### 5.4.3 操作步骤

| 步骤 | 说明 |
|------|------|
| 1. 在接口关键字列表或详情页点击「删除」 | 系统自动执行依赖检查 |
| 2a. 无引用 | 弹出确认弹窗「确定删除该接口关键字？」，点击「确认」执行删除 |
| 2b. 有引用 | 弹出依赖详情弹窗，标题「无法删除」，列出引用该关键字的 Action 列表（名称、分类、被用例引用数），每个 Action 可展开查看关联用例 |
| 3. 解除依赖 | 根据弹窗指引进入 Action 编辑器移除引用节点，或解除 Action 与用例的关联 |
| 4. 重新删除 | 解除所有引用后重新点击「删除」，此时无引用可正常删除 |

#### 5.4.4 字段说明

| 字段 | 来源 | 说明 | 协议 |
|------|------|------|------|
| 依赖检查结果 | 系统检查 | 是否有 Action 引用 | `DELETE /api/projects/:pid/keywords/:id` → `409` 时返回依赖信息 |
| 引用 Action 列表 | 系统查询 | Action 名称、分类、被用例引用数 | `GET /api/projects/:pid/keywords/:id/dependencies` → `actions[]` |
| 关联测试用例 | 系统查询 | 用例名称、所属套件、优先级 | `dependencies.actions[].cases[]` |

### 5.5 【KW-005】接口关键字传参与返回

#### 5.5.1 需求描述

接口关键字在 Action 节点中被调用时，支持灵活的数据流转：通过 `args` 覆盖预设测试数据，通过 `save_as` 将响应存入上下文变量。

#### 5.5.2 业务规则

##### 5.5.2.1 传参机制

需求：
1. 接口关键字在创建时配置预设测试数据（`test_data`）
2. 调用方（Action 节点）通过 `args` 覆盖预设测试数据中的部分或全部参数值
3. 参数值支持变量引用 `${var}`
4. 未覆盖的参数使用预设测试数据中的值

##### 5.5.2.2 返回机制

需求：
1. 执行后返回 HTTP 响应（状态码、响应头、响应体）
2. 调用方通过 `save_as` 将响应体存入执行上下文变量
3. 下游节点可通过 `${变量名}` 引用该响应数据
4. 支持 `expected_response` 定义预期响应，执行时自动断言

数据流转：`预设测试数据 → args 外部覆盖 → 组装 HTTP 请求 → 发送请求 → 响应体通过 save_as 存入上下文 → 下游通过 ${变量名} 引用`

接口关键字调用数据流转流程：

```
┌────────────────────────────────────────────────────────────────────────┐
│  Action 节点调用接口关键字                                              │
│                                                                        │
│  ① 传参阶段                                                            │
│  ┌──────────────┐     ┌──────────────┐     ┌─────────────────────┐     │
│  │ 预设测试数据   │     │ args 外部     │     │ 合并最终参数         │     │
│  │ (test_data)   │────▶│ 覆盖部分参数   │────▶│ args覆盖的用args值   │     │
│  │ page=1        │     │ page=${pg}   │     │ 未覆盖的用预设值      │     │
│  │ size=10       │     │ (仅覆盖page)  │     │ → page=${pg},size=10│     │
│  └──────────────┘     └──────────────┘     └──────────┬──────────┘     │
│                                                       ▼                │
│  ② 执行阶段                                                            │
│  ┌──────────────┐     ┌──────────────┐     ┌─────────────────────┐     │
│  │ 变量解析      │     │ 组装 HTTP     │     │ 发送请求             │     │
│  │ ${pg}→实际值  │────▶│ 请求          │────▶│ → HTTP 响应          │     │
│  └──────────────┘     │ path+method  │     │ (状态码+响应体)      │     │
│                       │ +body+header │     └──────────┬──────────┘     │
│                       └──────────────┘                ▼                │
│  ③ 返回阶段                                                            │
│  ┌──────────────┐     ┌──────────────┐     ┌─────────────────────┐     │
│  │ expected_    │     │ save_as 存入  │     │ 下游节点引用         │     │
│  │ response     │────▶│ 执行上下文     │────▶│ ${变量名}            │     │
│  │ 自动断言      │     │ 变量名=响应体 │     │ 获取上游响应数据      │     │
│  └──────────────┘     └──────────────┘     └─────────────────────┘     │
└────────────────────────────────────────────────────────────────────────┘
```

### 5.10 【TOOL-005】工具方法关键字传参与返回

#### 5.10.1 需求描述

工具方法关键字通过 `parameters` 定义输入参数，通过 `return` 返回结果，支持变量引用和数据流转。

#### 5.10.2 业务规则

##### 5.10.2.1 传参机制

需求：
1. 通过 `parameters` 字段定义输入参数（名称、类型、是否必填、默认值、说明）
2. 调用方通过 `args` 传入实际参数值
3. 参数值支持变量引用 `${var}`
4. 必填参数未传值且无默认值时，执行前报错

##### 5.10.2.2 返回机制

需求：
1. 通过 `return` 语句返回结果
2. 调用方通过 `save_as` 将返回值存入执行上下文变量
3. 下游节点可通过 `${变量名}` 引用
4. 未设置 `save_as` 时，返回值仅记录在执行日志中

工具方法关键字执行流程：

```
调用方传入 args 参数
  ↓
变量解析（${var} → 实际值）
  ↓
必填参数校验
  ├── 必填参数未传值且无默认值 → 执行前报错，中止
  └── 参数校验通过
        ↓
  沙箱安全检查
  ├── 包含禁止操作（os/sys/requests） → 拒绝执行
  └── 检查通过
        ↓
  ┌──────────────────────────┐
  │  沙箱执行 Python 函数      │
  │  超时控制：5s              │
  │  内存限制：64MB            │
  └────────────┬─────────────┘
               ▼
        ┌──────┴──────┐
        ▼             ▼
    执行成功       超时/异常
    return 值     抛出错误
        ▼             ▼
  save_as?        记录错误日志
  ├── 有 → 存入执行上下文变量，下游可 ${变量名} 引用
  └── 无 → 返回值仅记录在执行日志中
```

### 5.13 【ACT-002】Action 编辑器

#### 5.13.1 需求描述

Action 编辑器是核心编排功能，提供基于 AntV X6 的可视化流程图节点编排器，支持通过拖拽、连线的方式编辑业务逻辑，自由组合关键字和逻辑控制节点。

#### 5.13.2 业务规则

需求：
1. 基础信息：名称、描述、分类、标签
2. 输入参数：名称、类型、是否必填、默认值、说明（用例调用时传入）
3. 输出参数：名称、类型、说明（Action 执行后返回给用例）

##### 5.13.2.2 节点编排器

背景：Action 通过基于 AntV X6 的可视化流程图编排器组合关键字节点和控制流节点，形成可复用的业务动作单元。用户通过流程图方式直观编辑业务逻辑。**流程画布是 Action 关键字的执行蓝图：当 Action 被调试或被测试用例调用时，执行引擎严格按照流程画布中节点间的连线关系和拓扑顺序依次执行各节点，画布上未连线的孤立节点不参与执行。**

需求：
1. 可视化流程图编排界面，三栏布局：
   - 左侧元素面板（180px）：按元素类型分类展示用户已创建的关键字列表（接口关键字、工具方法关键字、Action 关键字、监听器、断言），各分类可折叠展开并含搜索框实时过滤，拖拽或双击单个关键字添加对应类型的节点到画布（双击时节点放置在画布可见区域中央并自动选中）
   - 中间流程图画布（弹性宽度）：基于 AntV X6 的流程图编辑器，支持节点自由定位、连线创建、画布缩放平移、网格对齐辅助线；顶部工具栏提供放大/缩小/适应画布/删除选中/一键格式化/一键清空操作；右键画布空白区弹出插入元素菜单（含搜索），在鼠标位置插入所选关键字节点
   - 右侧属性面板（280px）：选中节点的配置表单，根据节点类型动态切换

2. 节点类型：

| 节点类型 | 形状 | 说明 |
|----------|------|------|
| Action 关键字 | 方形（橙色） | 引用其他 Action 关键字，通过 `args` 传入参数，通过 `save_as` 保存输出为变量；支持 Action 嵌套调用 |
| 接口关键字 | 方形（蓝色） | 引用接口关键字（API），通过 `args` 传入输入参数，通过 `save_as` 保存输出为变量 |
| 工具方法关键字 | 方形（绿色） | 引用工具方法关键字（Tool），通过 `args` 直接传参，通过 `save_as` 保存返回结果 |
| 逻辑判断 | 菱形（紫色） | 条件表达式使用 **Python 语法**；有两个分支出口：「是」（满足条件，右侧）和「否」（不满足条件，下方） |
| 监听器 | 方形（灰色） | 待定义功能，占位节点 |
| 断言 | 方形（红色） | 对上游节点的执行结果进行校验，支持 6 种断言类型（equal/not_equal/include/not_include/true/not_true），配置实际值表达式和预期值，校验失败则标记该节点为失败状态 |

3. 串行与并行通过连线表达：
   - **串行**：节点间单线连接，依次执行
   - **并行**：一个节点多条出线分别连向不同节点（扇出），这些节点同时执行；多条出线汇合到同一节点时并行结束
4. 节点间变量传递：上游节点的 `save_as` 变量可在下游节点通过 `${var}` 引用
5. 流程图交互：
   - 从左侧面板拖拽或双击节点添加到画布（双击放置在画布可见区域中央并自动选中）
   - 通过节点连接桩拖拽创建连线（方形节点：上入/下出；菱形节点：上入/右侧「是」/下方「否」）
   - 逻辑判断节点的连线自动标注「是」/「否」分支标签
   - 画布支持鼠标滚轮缩放、拖拽平移
   - 选中节点后右侧属性面板动态展示对应配置
   - 曼哈顿路由算法自动计算连线路径
6. 流程画布执行语义：
   - 流程画布中节点间的连线关系定义了 Action 的执行路径，执行引擎按拓扑排序依次执行各节点
   - 串行节点依次执行，并行节点（扇出连线）同时执行，汇合节点等待所有并行分支完成后继续
   - 逻辑判断节点根据条件表达式结果选择「是」或「否」分支执行，未命中的分支跳过
   - 当 Action 关键字被其他 Action 或测试用例调用时，执行引擎读取该 Action 的流程画布数据并按画布定义执行

#### 5.13.3 操作步骤

| 步骤 | 说明 |
|------|------|
| 1. 点击「新建 Action」 | 进入编辑页，上方基础信息表单，下方流程图编排器 |
| 2. 填写基础信息 | 名称、描述、分类、标签，定义输入/输出参数 |
| 3. 添加节点 | 从左侧节点面板拖拽或双击节点到中间流程图画布（双击放置在画布中央） |
| 4. 连线构建流程 | 从节点连接桩拖拽到目标节点连接桩创建连线；单线=串行，扇出多线=并行；逻辑判断节点有「是」「否」两个分支出口 |
| 5. 配置节点属性 | 选中节点后在右侧属性面板配置（关键字选择、args 映射、save_as 等） |
| 6. 保存 | 点击「保存」按钮保存 Action 关键字，流程图自动序列化为节点树 |

| 变更点 | 变更前 | 变更后 |
|--------|--------|--------|
| 套件管理 | 无（新平台） | 左侧分组树 + 右侧套件列表表格，支持分组管理和批量操作，含 Setup/Teardown 配置 |

##### 6.1.2.2 Setup/Teardown 生命周期

背景：测试套件执行时需要在用例执行前后自动运行初始化或清理操作。系统支持四层 Setup/Teardown，四种均可独立配置，也可都不配置。

需求：
1. **套件级·整体** Setup/Teardown（独立开关）：Setup 在**整个套件**执行前调用一次，Teardown 在**整个套件**执行后调用一次
2. **套件级·每条** Setup/Teardown（独立开关）：Setup 在套件中**每条**用例执行前调用，Teardown 在**每条**用例执行后调用（所有用例共享相同步骤）
3. **套件内用例级** Setup/Teardown：在套件上下文中为**每条用例**单独配置差异化的 Setup/Teardown，仅在该套件执行该用例时生效（有步骤即生效，无需额外开关）
4. **用例级** Setup/Teardown：每条用例自行配置（在用例编辑器中，有步骤即生效，在所有场景通用）
5. 四种 Setup/Teardown 步骤结构均与用例步骤树相同（关键字步骤 + 控制流步骤），通过独立的迷你编排器配置
6. 四种全部配置时的嵌套执行顺序：

```
套件开始执行
  ↓
① Suite Setup（整体，enable_once=true 时仅执行一次）
  ↓
┌─── 遍历套件内用例 ──────────────────────────────────────────────────┐
│                                                                      │
│  ② Suite Setup（每条，enable_per_case=true 时执行）                   │
│    ↓                                                                 │
│  ③ Suite-Case Setup（套件内用例级，有步骤时执行）                       │
│    ↓                                                                 │
│  ④ Case Setup（用例级 setup_steps，有步骤时执行）                      │
│    ↓                                                                 │
│  ⑤ Case 步骤（steps）                                                 │
│    ↓                                                                 │
│  ⑥ Case Teardown（用例级 teardown_steps，有步骤时执行）                 │
│    ↓                                                                 │
│  ⑦ Suite-Case Teardown（套件内用例级，有步骤时执行）                    │
│    ↓                                                                 │
│  ⑧ Suite Teardown（每条，enable_per_case=true 时执行）                 │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
  ↓
⑨ Suite Teardown（整体，enable_once=true 时仅执行一次）
  ↓
套件执行结束
```

7. 错误处理策略：
   - Setup 失败：跳过当前用例/套件后续步骤，该用例标记为 ERROR
   - Teardown 失败：不影响用例执行结果，但在报告中单独记录 Teardown 错误
   - Setup/Teardown 执行日志与用例步骤日志分区展示

8. UI 配置区域：套件详情区「描述」字段下方新增可折叠的 Setup/Teardown 面板，包含：
   - **套件级·整体**区域：启用开关 + Setup/Teardown 迷你编排器（默认收起）
   - **套件级·每条**区域：启用开关 + Setup/Teardown 迷你编排器（默认收起）
   - 两个区域完全独立，可同时启用、可只启用一个、可都不启用

9. 套件内用例级配置：套件用例列表每条用例的操作列增加「Setup/Teardown」按钮，点击弹出独立配置弹窗，包含：
   - Setup 迷你编排器：为该用例在当前套件中配置差异化的 Setup 步骤
   - Teardown 迷你编排器：为该用例在当前套件中配置差异化的 Teardown 步骤
   - 已配置的用例在列表中显示 Setup/Teardown 标记徽章

### 6.3 【CASE-003】用例编辑器

#### 6.3.1 需求描述

用例编辑器是测试用例编排的核心功能，提供拖拽式步骤编排器，支持嵌套逻辑控制、校验配置和参数化数据驱动。

#### 6.3.2 业务规则

##### 6.3.2.1 基础信息

需求：
1. 用例名称、描述、前置条件、优先级（P0/P1/P2/P3）、标签
2. 用例级 Setup/Teardown（可选）：在用例步骤树前后各增加一个可折叠区域，分别配置 Setup 步骤序列和 Teardown 步骤序列，步骤结构与主步骤树相同

##### 6.3.2.2 步骤编排器

背景：测试用例由多个步骤组成，每个步骤调用关键字或控制流节点。步骤编排器采用三栏布局，与 Action 编辑器保持一致的交互体验。

需求：
1. 三栏布局：
   - 左侧步骤面板（200px）：可拖拽步骤类型列表
   - 中间步骤树（弹性宽度）：已添加的步骤树展示，支持拖拽排序/嵌套
   - 右侧属性面板（280px）：选中步骤的配置表单

2. 步骤类型：

| 步骤类型 | 说明 |
|----------|------|
| 关键字步骤 | 统一引用 Keyword 实体，传入输入参数，保存输出变量；支持按 keyword_type 筛选（API / TOOL / ACTION），可直接调用接口关键字、工具方法关键字或 Action 关键字 |
| 串行节点 | 子步骤按顺序执行 |
| 并行节点 | 子步骤同时执行 |
| 条件节点 | 根据变量表达式走 then/else 分支 |
| 等待节点 | 固定等待时长 |

3. 变量引用：通过 `${变量名}` 引用上游步骤的输出变量或环境变量

##### 6.3.2.3 校验配置

需求：
1. 每个关键字步骤可配置 0 到多个校验（断言），未配置校验的步骤仅执行不断言
2. 校验类型：

| 校验类型 | 说明 |
|----------|------|
| equal | 实际值等于预期值 |
| not_equal | 实际值不等于预期值 |
| include | 实际值包含预期值 |
| not_include | 实际值不包含预期值 |
| true | 实际值为真 |
| not_true | 实际值为假 |

3. 校验配置项：断言类型、实际值（支持 `${变量名}`）、预期值、校验描述

用例组成形式：
- **测试步骤 + 校验**：步骤执行后通过断言验证结果，适用于需要明确验证的场景
- **仅测试步骤**：步骤执行后不做断言，仅记录执行日志，适用于流程验证或前置准备场景

用例步骤执行与校验流程：

```
用例开始执行
  ↓
① 执行 Case Setup（setup_steps，如已配置）
  ↓
遍历步骤树（按节点类型执行）
  ↓
┌──────────────────────────────────────────────────────────────┐
│  当前步骤类型判断                                              │
│                                                              │
│  ┌─── 串行节点 ───┐  子步骤按顺序依次执行                      │
│  ┌─── 并行节点 ───┐  子步骤同时执行，全部完成后继续              │
│  ┌─── 条件节点 ───┐  解析 ${var} 表达式                       │
│  │                │  ├── true  → 执行 then 分支               │
│  │                │  └── false → 执行 else 分支               │
│  ┌─── 等待节点 ───┐  固定等待 duration_ms 毫秒后继续           │
│  ┌─ 关键字步骤 ──┐                                           │
│  │               ▼                                           │
│  │  ① 解析 args（变量引用 ${var} → 实际值）                    │
│  │  ② 调用关键字（接口关键字→发送HTTP / 工具方法关键字→沙箱执行 / Action 关键字→执行业务动作编排）│
│  │  ③ save_as 将结果存入执行上下文变量                         │
│  │  ④ 配置了校验？                                            │
│  │     ├── 有校验 → 逐条执行断言                               │
│  │     │           ├── 全部通过 → 步骤状态 PASSED              │
│  │     │           └── 任一失败 → 步骤状态 FAILED + 记录错误    │
│  │     └── 无校验 → 步骤状态 = 执行结果（成功=PASSED/异常=FAILED）│
│  └───────────────┘                                           │
└──────────────────────────────────────────────────────────────┘
  ↓
全部步骤执行完毕
  ↓
② 执行 Case Teardown（teardown_steps，如已配置）
  ↓
汇总用例结果（PASSED / FAILED / ERROR）
```

### 8.4 【RPT-004】历史对比

#### 8.4.1 需求描述

支持选择两次执行记录进行对比，从通过率、新增失败、修复用例、耗时等维度快速发现回归问题。

#### 8.4.2 业务规则

##### 8.4.2.1 选择执行记录

需求：
1. 页面顶部提供两个并排的下拉选择器：「执行记录 A」和「执行记录 B」
2. 下拉选项展示：测试计划 + 执行时间 + 状态徽章，支持搜索
3. 默认选择最近两次执行记录（A=倒数第二次，B=最近一次）
4. 点击「开始对比」按钮执行对比分析
5. 两次执行必须属于同一项目（同一计划更佳，但不强制）

##### 8.4.2.2 概要对比

需求：
1. 三列网格布局：
   - 左列：执行 A 数据（通过率、总耗时、总用例数、通过数、失败数、跳过数）
   - 中列：差异指标（通过率变化 ↑ 绿色 / ↓ 红色、耗时变化、失败数变化）
   - 右列：执行 B 数据（同左列指标）
2. 差异指标使用箭头和颜色标识变化方向

##### 8.4.2.3 差异明细

需求：
1. 三个标签页：
   - **新增失败用例**：执行 A 通过但执行 B 失败的用例（表格：用例名称、所属套件、错误摘要）
   - **修复用例**：执行 A 失败但执行 B 通过的用例（表格：用例名称、所属套件、原错误摘要）
   - **持续失败用例**：两次执行均失败的用例（表格：用例名称、所属套件、两次错误摘要对比）
2. 每个标签页标题旁显示数量徽章

##### 8.4.2.4 耗时对比

需求：
1. 双柱状图展示每个共用用例在两次执行中的耗时差异
2. 横轴为用例名称，纵轴为耗时（毫秒）
3. 执行 A 和执行 B 使用不同颜色柱状图并列展示
4. 支持鼠标悬停显示具体耗时数值

| 变更点 | 变更前 | 变更后 |
|--------|--------|--------|
| 历史对比 | 无（新平台） | 选择两次执行记录多维度对比，发现回归问题 |

#### 8.4.3 操作步骤

| 步骤 | 说明 |
|------|------|
| 1. 进入项目概览页 | 页面展示历史对比区块，包含两个执行记录选择器和「开始对比」按钮 |
| 2. 选择执行记录 | 分别在下拉框中选择执行 A 和执行 B（支持搜索） |
| 3. 点击「开始对比」 | 系统分析两次执行差异，展示对比结果 |
| 4. 查看概要对比 | 三列布局查看两次执行的指标数据和差异变化 |
| 5. 查看差异明细 | 切换标签页查看新增失败/修复/持续失败用例列表 |
| 6. 查看耗时对比 | 底部双柱状图查看各用例耗时差异 |

#### 8.4.4 字段说明

| 字段 | 来源 | 说明 | 协议 |
|------|------|------|------|
| 执行记录 A | 用户选择 | 对比基准执行记录 | `GET /api/projects/:pid/analytics/compare` → `execution_a_id` |
| 执行记录 B | 用户选择 | 对比目标执行记录 | `execution_b_id` |

| 修复用例 | 系统比对 | A 失败但 B 通过的用例列表 | 响应 → `diff.fixed[]` |
| 持续失败用例 | 系统比对 | 两次均失败的用例列表 | 响应 → `diff.persistent_failures[]` |
| 耗时对比数据 | 系统计算 | 各用例在两次执行中的耗时数据 | 响应 → `diff.duration_comparison[]` |

   - **执行概要**：总数/通过/失败/跳过统计、通过率进度环、总耗时
   - **图表**：通过率饼图、用例结果分布条形图
   - **详细结果表格**：每条用例的名称、状态、耗时、错误摘要
   - **失败用例详情**：失败用例的步骤级请求/响应日志和断言结果
2. 导出时显示 Loading 状态「正在生成 PDF...」
3. 生成完成后自动触发浏览器下载

##### 8.5.2.2 Excel 导出

需求：
1. Excel 文件包含以下 Sheet：
   - **概要** Sheet：执行信息、统计数字、通过率
   - **用例结果** Sheet：用例名称、所属套件、优先级、状态、耗时、错误摘要
   - **步骤详情** Sheet：失败用例的步骤级详细信息（步骤名、请求 URL、响应状态码、断言结果）
2. 结构化数据格式，便于二次分析和数据透视

##### 8.5.2.3 导出范围

需求：
1. **单次执行报告**：在执行详情页或执行历史页，导出某次执行的完整报告

3. 导出按钮位置：
   - 执行详情页右上角「导出」下拉按钮（PDF / Excel）
   - 执行历史页批量导出（勾选多条后「批量导出」）
   - 项目概览页通过率趋势区块右上角「导出报告」按钮

## 9. 用户认证

### 9.1 【AUTH-001】登录

#### 9.1.1 需求描述

平台提供用户名 + 密码登录，使用 JWT Token 认证（Access Token + Refresh Token），支持记住登录状态。

#### 9.1.2 业务规则

##### 9.1.2.1 JWT 认证策略

背景：第一期采用简单登录方案，管理员创建账号，用户登录使用。用户自助注册功能后续迭代。

需求：
1. 用户名 + 密码登录
2. JWT Token 认证（Access Token + Refresh Token）
   - Access Token 有效期 2h
   - Refresh Token 有效期 7d
3. 记住登录状态

| 变更点 | 变更前 | 变更后 |
|--------|--------|--------|
| 认证方式 | 无（新平台） | JWT 双 Token 认证，Access Token 2h + Refresh Token 7d |

JWT 认证流程：

```
┌──────────────────────────────────────────────────────────────┐
│  登录阶段                                                     │
│                                                              │
│  用户输入用户名 + 密码 → POST /api/auth/login                  │
│       │                                                      │
│       ├── 验证失败 → 返回 401 + 错误提示                       │
│       │                                                      │
│       └── 验证成功                                             │
│            ├── 生成 Access Token（有效期 2h）                   │
│            ├── 生成 Refresh Token（有效期 7d）                  │
│            └── 返回 { access_token, refresh_token, expires_in }│
└──────────────────────────────────────────────────────────────┘
                          ▼
┌──────────────────────────────────────────────────────────────┐
│  请求认证阶段                                                  │
│                                                              │
│  前端携带 Authorization: Bearer {access_token} 请求 API        │
│       │                                                      │
│       ├── Token 有效 → 正常响应请求                             │
│       │                                                      │
│       ├── Token 过期（401）                                    │
│       │    ├── 前端自动发起 POST /api/auth/refresh             │
│       │    │    ├── Refresh Token 有效 → 返回新 Access Token    │
│       │    │    │    └── 前端重试原始请求（用户无感知）          │
│       │    │    └── Refresh Token 过期 → 跳转登录页              │
│       │    └──                                              │
│       │                                                      │
│       └── Token 无效 → 跳转登录页                              │
└──────────────────────────────────────────────────────────────┘
                          ▼
┌──────────────────────────────────────────────────────────────┐
│  登出阶段                                                     │
│                                                              │
│  POST /api/auth/logout → 服务端标记 Token 失效                 │
│  前端清除本地存储的 Token → 跳转登录页                          │
└──────────────────────────────────────────────────────────────┘
```

### 9.2 【AUTH-002】用户管理（管理员）

#### 9.2.1 需求描述

管理员管理用户：创建、编辑、禁用用户，基于角色的权限控制（RBAC）。不支持用户自助注册。

#### 9.2.2 业务规则

##### 9.2.2.1 角色权限定义

| 角色 | 权限 |
|------|------|
| ADMIN | 全权限：所有功能操作 + 用户管理 + 系统配置 |
| USER | 测试操作权限：项目、接口、关键字、用例、执行等（不可管理用户和系统配置） |

> **前端权限表现**：顶部用户头像下拉菜单中的【系统设置】仅对 ADMIN 角色显示；USER 角色登录时该菜单项隐藏。

##### 9.2.2.2 用户 CRUD

需求：
1. 用户列表：用户名、姓名、角色（ADMIN=紫色 tag / USER=蓝色 tag）、状态、创建时间、最近登录时间
2. 管理员手动创建/编辑/禁用/删除用户
3. 重置密码功能
4. **用户删除规则**：除账号为 `admin` 的系统内置管理员外，其他用户均允许删除；删除前需弹出确认弹窗进行二次确认，删除后数据不可恢复。
5. **账号保留规则**：新建用户或修改账号时，账号（`username`）不能使用 `admin`（不区分大小写），该账号为系统内置管理员专用；前端校验不通过时显示错误提示并阻止提交。
6. **用户名保留规则**：新建用户或修改用户名时，用户名（`display_name`）不能为「管理员」，该名称为系统保留，仅供 `admin` 账号使用；前端校验不通过时显示错误提示并阻止提交。

#### 9.2.3 操作步骤

| 步骤 | 说明 |
|------|------|
| 1. 进入「用户管理」页面 | 工具栏搜索框 + 角色筛选下拉 |
| 2. 新建用户 | 点击「新建用户」→ 弹窗填写用户名、姓名、密码、角色、状态 |
| 3. 编辑用户 | 点击「编辑」→ 弹窗修改姓名、角色、状态 |
| 4. 禁用/启用用户 | 点击「禁用/启用」按钮切换用户状态 |
| 5. 删除用户 | 点击「删除」→ 确认弹窗二次确认 → 删除用户（admin 账号不显示删除按钮） |
| 6. 重置密码 | 点击「重置密码」→ 输入新密码 → 确认 |

| 交互 | 规范 |
